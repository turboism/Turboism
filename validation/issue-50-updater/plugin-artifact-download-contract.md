# Plugin Download Acceleration Client Contract

This change covers the client only; the other side implements and deploys the two server paths. The final contract is [#67](https://github.com/turboism/Turboism/issues/67) and the server implementation is the separate PR #66. Finished code does not mean manual activation is complete.

1. The signed catalog still comes from `https://plugin.turboism.dev/api/v2/catalog.json` with its own signature. The GitHub Release URLs inside the catalog stay unchanged.
2. After verifying the catalog, the client first requests `GET https://api.turboism.dev/v1/plugins/artifacts/{sha256}/{filename}`. The SHA-256 and the file name including the `.jar` extension come directly from the Ed25519-verified `release.artifact.sha256` and `fileName`, never from a URL or unsigned data.
3. The endpoint must answer 302, and the Location must be `https://dl.turboism.dev/plugins/{sha256}/{filename}` with the same SHA-256 and the same file name. No other host, path, query parameter, or second CDN redirect is accepted.
4. When the API or CDN is not deployed, a mirror is missing, a rate limit or 5xx service failure occurs, TLS fails, the network times out or drops, the download truncates, or the size or hash check fails, the client discards the written file and falls back to the GitHub Release URL from the signed catalog, still under the original GitHub CDN redirect allowlist. An acceleration attempt may use at most 15 seconds and leaves the original download its total budget; the whole download stays under the overall deadline.
5. Both paths must pass the catalog's real size, SHA-256, descriptor hash, plugin ID, version, and permission checks plus the existing installation rollback checks. After a fallback the client downloads from zero and re-verifies completely; it never concatenates files from different sources. A failed GitHub file check still rejects the installation. A cancellation, a disk write or cleanup failure, and a non-conforming redirect do not trigger a fallback.

The server side publishes only JARs that are already published in the signed catalog, not withdrawn, and byte-verified. The CDN file endpoint supports GET, HEAD, Range, If-Range, and If-None-Match with ETag; a full download answers 200 and a partial download answers 206, cached for 60 seconds. A HEAD result, an ETag, or a hash in the URL never replaces a full byte check. This client still issues a full GET and adds no resumable download.

Marketplace installation, background plugin auto-update, and the unified framework and plugin update window all share `PluginCatalogClient.downloadArtifact`, so they use the same acceleration, fallback, and verification logic. Enabling acceleration needs no catalog change and no re-signing.
