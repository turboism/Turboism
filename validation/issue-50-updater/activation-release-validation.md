## API Refresh Fault After the First Release

Beta.5 was published, but around 09:23 UTC the public API still returned Beta.1 / Build 73 with the snapshot time stuck at `2026-11-01T08:52:40.266Z` and health `degraded`. The notification workflow only checked whether a channel was `unavailable`, so it still reported success while serving the old snapshot.

The [read-only production diagnostic 41292738844](https://github.com/turboism/turboism-learn/actions/runs/41292738844) captured 7 records with 2 `Release refresh failed: GitHub HTTP 403` entries. The local run read the public GitHub metadata with the same server validator, all three channels passed, and it identified Beta.5 / Build 79; the complete release list was only about 1.4 MB and never reached the 4 MB limit. A refused production GitHub request is proven, and the response headers that would distinguish the exact rate-limit type were not captured.

The fix lets the existing trusted OIDC notification carry the short-lived `contents: read` credential of that job, used only for this pinned GitHub API read. The credential travels in a bounded POST request body and never enters a snapshot, a download object, the client, or a request URL or custom header. An authenticated refresh may retry immediately after an anonymous failure and waits for an in-flight anonymous refresh to finish; an ordinary public call still cannot supply a credential or trigger an internal refresh. A new trusted notification runs every ten minutes, and the Cloudflare Cron stays as the anonymous fallback for a stale snapshot. The notification fails after a bounded retry when it meets a degraded, stale, or incomplete result.

Nightly packaging additionally found that a worker thread exited late after a cancelled download. The original Linux test reproduced it on the 27th repetition; a re-check that captured stacks only after the failure reproduced it again on the 23rd, confirming that the download thread waited on a stream lock held by the JDK `Keep-Alive-SocketCleaner`. When the cancel scheduler and the download thread closed the response concurrently, the background cleanup kept reading the cancelled response, so the exit exceeded the original 7-second limit. A control that only sent `Connection: close` still reproduced it, because the server may not return a close flag. The final fix lets the download thread clean up uniformly after a bounded connect and read return; a cancel still completes the future immediately and interrupts the worker, and no blocking close runs on the caller or the shared scheduler. The original 7-second assertion stays, and new assertions verify that the scheduler responds within 1 second, that a cancel or timeout retries successfully at once, and that the old future stays failed. The new scheduler assertions failed before the Windows Java 17 fix and passed after it, and the final implementation ran 10 repetitions green; the complete Linux downloader passed 72 cases with no skip. A longer cancel comparison and a new full CI were still running.
