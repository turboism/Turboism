Acceptance finding
- Corrupt plugin application rolls back directory bytes and prevents mistaken framework health.
- But a retained corrupt plugin journal blocks the entire extension runtime until repaired.
  User-visible failure/retry/repair and degraded old-plugin startup policy remain qualification gaps.
  No claim that the updater automatically repairs this condition, or that both journals are atomic.

B. Backup preparation data-loss defect found and fixed (e72137dec)
- Review of the exercised rollback path found that failure DURING backup creation still entered
  restore(). A partial backup could replace otherwise good live JARs.
- Added two fault-injection tests: fail first backup and fail second after one succeeds, leaving a
  one-byte partial file. Before the phase fix, both failed: live JAR lengths 803/804 became 1 byte.
  This is portable injected-IO evidence, not a physical full-disk/power-loss test.
- Fix separates backup preparation from live mutation. Backup failure returns RECOVERY_REQUIRED /
  PLUGIN_PENDING_BACKUP_FAILED without restoring over live files. Only this attempt's own created
  backup directory is eligible for cleanup. Journal/consent stay unchanged; startup remains blocked.
- Backup and restore use no-follow, complete-write-loop snapshots with force(true); failed restore
  still reports recovery-required. No startup admission/safety guard was relaxed.
- Selected update/plugin/window regression: 485 tests, zero failures/errors, 6 skips. Bootstrap JAR
  and license checks pass; core-contract retains its 31-test green result.
