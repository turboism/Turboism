# Full-Installation Version and Full-Current-Capability Verification

Goal: keep expanding the version coverage until every currently installed version has verified the current framework capabilities, and finally deliver the supported and unsupported capability set of each version.

The scope baseline is the SDK, runtime capabilities, plugins, and existing verification scenarios of `7d7de1de4`. A fix committed later to achieve compatibility must enter the matching retest package. The goal must not shrink to a start, Core, or Workspace check, and a capability must not be excluded because the current task directory misses it.

## Current Scope

- All 20 actually installed Editor and Core instances had their file presence and Editor digest checked; the installation directory aliases `5.2` and `5.3` bind 5.2.03 and 5.3.02, so a version is never guessed from a directory name.
- `inventory.json` indexes the static capabilities, the 46 optional SDK services, the context members guaranteed to exist, the SDK source files, the 30 plugins, the current directory scenarios, and the unregistered verification scripts.
- `sdk-method-coverage.json` indexes the public and protected methods, constructors, fields, and nested types from the current SDK classfiles, including incubating API; the 21 owned-MOC methods, the 14 MCP texture, fixture preparation, and history methods, and the 27 MCP Glue, parameter, and binding methods are linked to explicit scenarios, and the remaining mapping awaits audit. A method mapping by itself produces no version support conclusion.
- `verification-table.md` is an intermediate ledger, not the final support table. No exact static record does not mean unsupported, and the compatibility admission path also needs investigation.
- `campaign-jobs.json` stores the identifiers of new host tasks; a submission state is no acceptance result. The runtime state must be queried again from the shared queue, and a terminal state must be checked against the supervisor evidence.

## Work Order

1. Complete the coverage mapping from capability to SDK operation, plugin behaviour, hook, and host scenario or assertion; audit the scripts outside the directory. A service existing proves only that the object registers, not that all its methods work.
2. Complete the version gates, exact digests, and assertion differences of the cross-version verification tooling. A task directory listing a version does not mean the wrapper really supports running it.
3. Establish a repeatable host startup plus model, PSD, animation, and texture atlas fixtures suited to the target version and licence mode. Always use a task copy; never modify the original model, the official installation, or the golden prefix.
4. Complete the native tuple observation for every distinct Core fingerprint, review the API differences, and establish an exact configuration or an explicit capability boundary. An existing Core acquisition success proves only its identity and model observation assertions, and NO_PUBLIC_BRIDGE does not prove Core structure reading.
5. Execute the real read, write, undo and restore, persistence, UI and hook, and plugin scenarios on every installed version according to the coverage mapping. Investigate whether a static mismatch can be adapted; when no adaptation path exists, record the specific unsupported evidence.
6. Fix the discovered problems, rebuild the immutable inputs, and retest the affected capabilities and versions. The other versions keep progressing, and one fixture or one test-infrastructure failure never stops the whole goal.
7. Output the final support matrix, the per-version supported and unsupported capability detail, the limitations, and the evidence index. Before completion, audit item by item whether the full scope is covered.

## Evidence Standard

- Supported: a capability assertion for that exact version and real artifact passes, bound to the job, the prepared digest, the artifact digest, the real host identity, and the final supervisor result.
- Unsupported: evidence of a specific missing API, selector, or runtime feature, or of an explicit unsupported response. A framework error must be fixed and never relabelled unsupported to finish the table.
- A timeout, an unregistered licence, an unsuitable fixture, a test script that rejects the version, and a missing scenario are all pending items and never masquerade as unsupported.
- A verification-only provider, manual assistance, a FREE limitation, a performance switch, and NO_PUBLIC_BRIDGE must have their effect recorded explicitly and must never be used to derive a wider production capability pass.
- Completion requires a sufficient conclusion for every version and every in-scope capability; PENDING or indirect evidence still means incomplete.
