# T029 首轮瓶颈测量（JFR，5303 / Circle100）

目的：回答“时间到底花在哪”，而不是继续扩证据链。这次测量不新增进程内探针，只复用已有的
JDK Flight Recording 方法与现成分析脚本。

## 方法与边界

- 载体：本目录的固定采集场景（`atlas-image-shadow:5303`），因为它执行的 `自动排版 → OK` 正是
  “载入/重建纹理集”那条真实路径；`atlas-image-observe` 走 Cancel，图像生成根本不发生，不适用。
- 开启方式：wrapper 的 run label 加 `-jfr` 后缀（默认关闭）。注入的仅有
  `-XX:StartFlightRecording=filename={HOME}\atlas-profiling.jfr,settings=profile,maxsize=256m,dumponexit=true`。
  不改变任何场景动作、参数或结果文件；录制文件落在 task-owned home 内，不触碰 fixture。
- 本次作业：seq 149，`queue-da4c837a712a40bcb15ee31b6c9d1a0b`，
  prepared `3f7fa28e99cd22c6129f66f06771988fc33c6acd813b5ccc2841204a1641db6b`，
  run label `atlas-t040-profiling-12-jfr`（倍率 40%，即 kernel 被真实调用的那一侧）。
  队列判定 `succeeded` / `validationStatus=PASS` / `normalExit=true` / `fixtureUnchanged=true`；
  payload 仍为 `TRUNCATED`、`recorded=64`、`admitted=64`、`potentialTrim=64`、`dropped=36`。
- 分析：`/usr/lib/jvm/java-17-openjdk/bin/jfr`（JDK 17）+ `/tmp/t040-jfr.json`
  （`jfr print --json --events jdk.ExecutionSample,jdk.NativeMethodSample`，5043 个采样）。
- 录制：88 s，Version 2.1，1 chunk。

## 结果

整轮 87.8 s 里，**唯一持续 CPU 密集的阶段就是纹理生成**（其余为启动类加载、EDT 空转与 socket 等待）：

| 项 | 值 |
|---|---|
| 纹理生成窗口 | **77.53 s – 85.26 s ≈ 7.73 s**（占整轮 8.8%） |
| 执行线程 | **`Thread-93` 单线程**（269/269 采样），不是 EDT，也没有并行 |
| 每次调用成本 | 约 **77 ms / 图**（100 图 / 7.73 s） |
| 调用链（实测栈） | `CTextureAtlas.setupCacheImage$cubism` → `com.live2d.util.D.a` → `com.live2d.util.f.g.a` |

窗口内非空闲采样（528 条）的 leaf frame 分解：

| 占比 | 帧 | 说明 |
|---|---|---|
| **45.3%** | `com.live2d.util.f.g.a` | 整数降采样 kernel —— T027-S 的优化对象 |
| 15.5% | `sun.java2d.loops.MaskBlit.MaskBlit` | Java2D alpha 混合 |
| 15.3% | `java.util.Arrays.fill` | 数组清零（触发者：`jp.noids.graphics.f.a` 57、kernel 内 24） |
| 7.2% | `jp.noids.graphics.h.a` | |
| 4.0% | `sun.java2d.pipe.DrawImage.blitSurfaceData` | |
| 其余 | `GifImageDecoder`、`ComponentColorModel.getDataElements`、`GDIBlitLoops` 等 | 各 <3% |

## 结论

1. **用户的观察被实测证实**：图像确实是**一个线程、一个一个**处理的（`Thread-93`）。当前页只有一页
   Atlas，所以“页级并行”在这个 fixture 上收益为 0；页内并行是规格明确的非目标。
2. **T027-S 打在了最大的单一热点上**（kernel 占窗口 45.3%），这条路线在“热点定位”上是对的。
   但它只跳过全透明源块，且明确不碰 `Arrays.fill`（另占 15.3%，多数来自 `jp.noids.graphics.f.a`），
   所以上限受限：即使 kernel 完全消除，也只省下窗口的 45%、即整轮的约 4%。
3. **单次操作里纹理生成并不是主要耗时来源**：7.7 s / 87.8 s。其余时间主要是宿主启动（约 18 s 类加载）
   与等待（EDT 空转、`HttpClient-*` selector 的 socket 等待）。后者是宿主自身行为，与图集算法无关。
4. 按图均摊 77 ms/图 偏高（100×100 的图、2×2 降采样），说明每图存在可观的固定开销，
   与 `Arrays.fill` + `MaskBlit` 合计约 31% 相符。


## 第二轮：生产尺度模型（`heavy.cmo3`）—— 回答“8.8% 是不是玩具数字”

用户提供了真实模型 `~/Downloads/heavy.cmo3`（SHA-256 `029e9a4e…`，446 MB），与仓库里既有的
perf-baseline / artmesh-perf fixture 是**同一个文件**，因此不是未知输入。场景新增 `-heavy` 运行标签：
切换 fixture 对（名 + 哈希成对白名单，驱动与 wrapper 两侧都校验）并提高墙钟预算（启动/关闭轮询 1800 s、
排版对话框 900 s、驱动 3600 s、结果 3600 s、退出 300 s）；默认标签的 Circle100 行为一字未改。

作业：seq 164，`queue-43feffa449874d47833259b92f54b0a6`，prepared
`42c7e20ac4b01107dc1e857acbf42d5e8bd7963a1c75ab04121541619c20c49e`，标签
`atlas-t040-profiling-13-heavy-jfr`（40% 倍率 + JFR）。队列 `succeeded` / `PASS` / `normalExit` /
`fixtureUnchanged`；payload `TRUNCATED`、`recorded=64`、`dropped=37`、`potentialTrim=64`，真实参数
**`kx=2 ky=2 padding=2 source=235×416 stride=240 destLen=159360`**（比 Circle100 的 100×100 大约 15 倍像素）。
JFR 457 s / 40 707 采样。

| 阶段 | 窗口 | 占整轮 | 主要 leaf frame |
|---|---|---|---|
| 宿主启动（类加载） | 0–59 s | 13% | 极端空转，仅 ~455 非空闲采样 |
| 文档加载（446 MB） | 60–179 s | 26% | `ImageRepresentation.setPixels`、`serialize.impl.G.a`、`getDataElements`、`FillRect` |
| 打开编辑器 + 自动排版 | 180–307 s | 28% | `HashMap$TreeNode.find`(2077)、`atlasEditor.a.b.h`(1661)、`triangulation.h.c`(1522) |
| **图集图像生成** | **308.2–434.9 s = 126.7 s** | **27.8%** | 见下 |
| 收尾（取图/退出） | 435–455 s | 4% | `getDataElements`、`OpaqueCopyArgbToAny.Blit`、`GifImageDecoder` |

图集生成窗口仍由**单线程 `Thread-103`** 完成（7447 采样），非空闲采样 7931 条的 leaf 分解：

| 占比 | 帧 | 与 Circle100 对比 |
|---|---|---|
| **43.2%** | `com.live2d.util.f.g.a` | 45.3% → 同为最大单一热点 |
| 17.9% | `java.util.Arrays.fill` | 15.3% → 上升 |
| 17.2% | `sun.java2d.loops.MaskBlit.MaskBlit` | 15.5% → 持平 |
| 9.8% | `jp.noids.graphics.h.a` | 7.2% |
| 3.9% | `TransformHelper.Transform` | 新增 |
| 3.2% | `GifImageDecoder.parseImage` | 新增 |

### 结论（取代上轮的“不能外推”）

1. **换到生产尺度后，纹理生成从 8.8% 升到 27.8%**（7.7 s → 127 s），并且是整轮里最大的单一 CPU 密集阶段。
   上一轮“fixture 太小”的怀疑成立：Circle100 确实低估了它。
2. 但**它不是唯一的大头**：文档加载（26%）与“打开编辑器 + 自动排版”（28%）合计占了 54%，
   两者都不在本 spec 范围内；其中排版阶段的 `HashMap$TreeNode.find` 热点（2077 采样）像是可查的独立问题。
3. 在 127 s 的图集生成里，**T027-S 的目标 kernel 只占 43.2%（≈55 s）**，而它明确不改的 `Arrays.fill` + `MaskBlit`
   合计 35.1%（≈45 s）。所以 T027-S 即使完美生效，上限也只是整轮的 ~12%，而它实际只跳过全透明源块。
4. 单图成本从 Circle100 的 77 ms 升到 ≈1.25 s（101 次调用 / 126.7 s），与像素量约 15 倍的增长一致——
   换言之这个阶段主要是**真实像素运算量**，不是固定开销。

## 第三轮：不排版（preserve）路径 —— 用户真实描述的“载入/保持纹理集”

场景新增 `-nolayout` 运行标签：完全跳过自动排版对话框，只打开纹理集编辑器 → 按 OK。这正是
“打开纹理集 / 保持原样 / 导出”时用户走的路。作业 seq 166，
`queue-a6023aeeb42c4f53b20d69bc4554c597`，prepared `58204fbe06…`，标签
`atlas-t040-nolayout-14-heavy-jfr`（heavy + JFR）。队列 `succeeded`/`PASS`/`normalExit`/`fixtureUnchanged`；
驱动证据 `layout.preserved=true`、`layout.attempted=false`、`layout.scaleText=NONE`。

| | 自动排版 40%（seq 164） | **不排版（seq 166）** |
|---|---|---|
| 整轮 | 455 s | **391 s** |
| OK→编辑器关闭 | 146 s | **172 s** |
| 图集生成（`setupCacheImage`）采样 | 3686 | **3815** |
| 整型降采样 kernel（T039 目标 `(II[III[IIIII)V`） | 100 次调用 | **0 次（`NO_CALLS`）** |
| 同族其它 `g.a` 重载 | 走 kernel 分支 | 走 Graphics2D 快路径 |
| 网格三角化 | 2708 采样 | **2161 采样（照样发生）** |
| `HashMap$TreeNode.find` | 2239 采样 | **2014 采样（照样发生）** |

### 结论（直接改写优化优先级）

1. **T027-S 在用户实际路径上收益为 0。** 不排版时有效缩放就是 1:1，`g.a` 走 Graphics2D 快路径，
   被 shadow 的 10 参整型 kernel 一次都不会被调用（`NO_CALLS`），而这条路依旧要花 **172 s**。
   之前“1:1 就 0 次调用”只在 Circle100 上看过，现在在真实模型上同样成立。
2. **不排版反而更慢**（172 s vs 146 s），因为 1:1 合成比 40% 降采样要处理更多像素。
   这也说明这段耗时主要是**真的像素搬运**（`setupCacheImage` 内部：临时图 + `Graphics2D.drawImage` +
   `Arrays.fill` 清屏 + `jp.noids.graphics.h.a`），不是靠“缓存/去重”能抺掉的重复计算。
3. **三角化与排版无关**：两轮都发生且量级相同，属于“打开纹理集编辑器”本身的开销。

## 附：`HashMap$TreeNode.find` 根因（先前误归为“排版阶段”热点，实为网格三角化）

两轮都落在同一处：`GEduitableMesh2.updateMesh` → `updateIndices` → `triangulation.h.a` →
`triangulation.h.c`（leaf 占比最高），运行在 **`AWT-EventQueue-0`**，与排版对话框无关。

只读反编译已定位根因：

- `com.live2d.graphics3d.editableMesh.triangulation.h` 持有 `private final Set<kotlin.Pair<l, l>> a;`
- `com.live2d.graphics3d.editableMesh.triangulation.l.hashCode()` 的字节码是 `iconst_0; ireturn`，
  即 **恒定返回 0**。
- `kotlin.Pair.hashCode()` = `31 * first.hashCode() + second.hashCode()`，两侧都是 0，于是**整个 Set
  的每个元素都落进同一个桶**；HashMap 冲突超阈值后把桶树化，`TreeNode.find` 便要在深树里逐层 `equals`，
  退化成接近 O(n)。

影响量级：真实模型上 `HashMap$TreeNode.find` 占 **2014–2239 采样**（两轮一致），与三角化总体
2000–2700 采样同量级，即整轮 391–455 s 中的约 **25–30% 墙钟** ≈ 1.5–2 分钟。

范围归属：这是 **`com.live2d.graphics3d.editableMesh`（宿主网格代码）**，与 020 的纹理集图像生成无关；
修它需要改写宿主三角化（还得兼顾 `l.equals` 语义），风险与验收面完全不同。本报告只做定位，不实施；
若要推进，应另立 feature 并单独裁决。

### 限制

- 仍然只有**每档 1 次运行**，没有重复与配对，依旧不能作为 SC-02/SC-04a 证据。
- 场景会把排版倍率固定为 40%；真实用户若不做自动排版，图集生成的量级会不同。
- 绝对耗时包含验证 harness（隔离 prefix、三个 agent、JFR 自身开销）的代价。
- JFR 采样是统计性的，只用于定位热点与阶段边界。
- 本轮仍是**纯测量**：没有改一行生产代码，也没有测“优化开/关”的配对。

## 限制（不得越过）

- **fixture 极小**：Circle100 = 100 张 100×100。真实模型若图像更大更多，纹理生成占比会显著上升，
  本轮的 8.8% **不能外推**为用户现场比例。
- 只有 **1 次运行**，没有重复与配对，不能作为 SC-02/SC-04a 的性能证据；`runElapsedMillis`
  与其它作业的差异不得当作收益或回归。
- JFR 采样是统计性的（约 50–100 采样/秒），只能定热点与阶段边界，不能给精确的逐方法耗时。
- 本轮**只测量**：没有改一行生产代码，也没有测过“优化开/关”的配对，因此**没有任何加速证据**。
- 该 JFR 是在验证 harness（隔离 prefix、agent、本机队列）内采集的，绝对值含 harness 开销。
