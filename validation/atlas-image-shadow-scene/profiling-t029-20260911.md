# T029 First-Round Bottleneck Measurement (JFR, 5303 / Circle100)

Goal: answer "where does the time actually go" instead of extending the evidence chain. This measurement adds no in-process probe and reuses only the existing JDK Flight Recorder method and the ready-made analysis script.

## Method and Boundary

- Carrier: the fixed capture scenario of this directory (`atlas-image-shadow:5303`), because its `automatic layout → OK` path is exactly the real "load and rebuild the texture atlas" path; `atlas-image-observe` goes through Cancel, so image generation never happens and it does not apply.
- Enabling: add the `-jfr` suffix to the wrapper run label (off by default). The only injected option is `-XX:StartFlightRecording=filename={HOME}\atlas-profiling.jfr,settings=profile,maxsize=256m,dumponexit=true`. It changes no scenario action, parameter, or result file; the recording lands in the task-owned home and never touches the fixture.
- This job: seq 149, `queue-da4c837a712a40bcb15ee31b6c9d1a0b`, prepared `3f7fa28e99cd22c6129f66f06771988fc33c6acd813b5ccc2841204a1641db6b`, run label `atlas-t040-profiling-12-jfr` (40% scale, the side that really calls the kernel). The queue reported `succeeded` / `validationStatus=PASS` / `normalExit=true` / `fixtureUnchanged=true`; the payload stayed `TRUNCATED` with `recorded=64`, `admitted=64`, `potentialTrim=64`, and `dropped=36`.
- Analysis: `/usr/lib/jvm/java-17-openjdk/bin/jfr` (JDK 17) plus `/tmp/t040-jfr.json` (`jfr print --json --events jdk.ExecutionSample,jdk.NativeMethodSample`, 5043 samples).

## Conclusions

1. **The user observation is confirmed by measurement**: the images really are processed **on one thread, one at a time** (`Thread-93`). The current page holds a single texture atlas page, so page-level parallelism gains nothing on this fixture; in-page parallelism is an explicit non-goal of the specification.
2. **T027-S hits the largest single hot spot** (the kernel is 45.3% of the window), so the route is right about hot-spot location. But it only skips fully transparent source blocks and explicitly leaves `Arrays.fill` alone (another 15.3%, mostly from `jp.noids.graphics.f.a`), so its ceiling is limited: even removing the kernel entirely saves only 45% of the window, about 4% of the whole run.
3. **Texture generation is not the dominant cost of a single operation**: 7.7 s of 87.8 s. The rest is mostly host startup (about 18 s of class loading) and waiting (EDT idling, socket waits of the `HttpClient-*` selector). The latter is host behaviour unrelated to the atlas algorithm.
4. An amortized 77 ms per image is high for a 100×100 image at 2×2 downsampling, which shows a sizeable fixed cost per image and matches `Arrays.fill` plus `MaskBlit` at about 31% combined.

### Conclusions (Replacing the Earlier "Cannot Extrapolate")

1. **At production scale, texture generation rises from 8.8% to 27.8%** (7.7 s to 127 s) and becomes the largest single CPU-intensive phase of the run. The earlier suspicion that the fixture was too small holds: Circle100 really did underestimate it.
2. But **it is not the only large cost**: document load (26%) and open editor plus automatic layout (28%) together take 54%, and neither is in the scope of this specification; the `HashMap$TreeNode.find` hot spot in the layout phase (2077 samples) looks like a separate investigable problem.
3. Inside the 127 s of atlas generation, **the T027-S target kernel is only 43.2% (about 55 s)**, while the `Arrays.fill` plus `MaskBlit` it explicitly leaves alone is 35.1% (about 45 s). So even a perfect T027-S caps out at about 12% of the run, and it really only skips fully transparent source blocks.
4. The per-image cost rises from 77 ms on Circle100 to about 1.25 s (101 calls in 126.7 s), consistent with the roughly 15× pixel growth; in other words this phase is mostly **real pixel work**, not fixed overhead.

## Third Round: No-Layout (Preserve) Path, the Real "Load and Keep the Atlas" the User Describes

The scenario gained a `-nolayout` run label that skips the automatic layout dialog entirely and only opens the texture atlas editor and presses OK. That is exactly the path a user takes to open a texture atlas, keep it as is, and export. Job seq 166, `queue-a6023aeeb42c4f53b20d69bc4554c597`, prepared `58204fbe06…`, label `atlas-t040-nolayout-14-heavy-jfr` (heavy plus JFR). The queue reported `succeeded` / `PASS` / `normalExit` / `fixtureUnchanged`; the driver evidence was `layout.preserved=true`, `layout.attempted=false`, and `layout.scaleText=NONE`.

| | Automatic layout 40% (seq 164) | **No layout (seq 166)** |
|---|---|---|
| Whole run | 455 s | **391 s** |
| OK to editor close | 146 s | **172 s** |
| Atlas generation (`setupCacheImage`) samples | 3686 | **3815** |
| Integer downsampling kernel (T039 target `(II[III[IIIII)V`) | 100 calls | **0 calls (`NO_CALLS`)** |
| Other `g.a` overloads of the same family | take the kernel branch | take the Graphics2D fast path |
| Mesh triangulation | 2708 samples | **2161 samples (still happens)** |
| `HashMap$TreeNode.find` | 2239 samples | **2014 samples (still happens)** |

### Conclusions (Directly Rewriting the Optimization Priority)

1. **T027-S gains nothing on the user's real path.** With no layout the effective scale is 1:1, `g.a` takes the Graphics2D fast path, the shadowed ten-argument integer kernel is never called (`NO_CALLS`), and that path still costs **172 s**. The earlier "1:1 means zero calls" was seen only on Circle100 and now holds on the real model too.
2. **No layout is actually slower** (172 s versus 146 s) because 1:1 compositing handles more pixels than 40% downsampling. This also shows that the cost is mostly **real pixel movement** (inside `setupCacheImage`: temporary image, `Graphics2D.drawImage`, `Arrays.fill` clearing, and `jp.noids.graphics.h.a`) and not repeated computation that caching or deduplication could wipe out.
3. **Triangulation is unrelated to layout**: it happens in both rounds at the same magnitude and belongs to opening the texture atlas editor itself.

## Appendix: Root Cause of `HashMap$TreeNode.find` (Previously Misattributed to the Layout Phase, Really Mesh Triangulation)

Both rounds land in the same place: `GEduitableMesh2.updateMesh` → `updateIndices` → `triangulation.h.a` → `triangulation.h.c` (the highest leaf share), running on **`AWT-EventQueue-0`**, unrelated to the layout dialog.

A read-only decompile located the root cause:

- `com.live2d.graphics3d.editableMesh.triangulation.h` holds `private final Set<kotlin.Pair<l, l>> a;`
- The bytecode of `com.live2d.graphics3d.editableMesh.triangulation.l.hashCode()` is `iconst_0; ireturn`, which **always returns 0**.
- `kotlin.Pair.hashCode()` is `31 * first.hashCode() + second.hashCode()`, and with both sides zero **every element of the whole Set lands in one bucket**; once the HashMap collisions pass the threshold the bucket becomes a tree, and `TreeNode.find` then walks a deep tree calling `equals`, degrading to nearly O(n).

Magnitude: on the real model `HashMap$TreeNode.find` takes **2014–2239 samples** (consistent across both rounds), the same order as the 2000–2700 triangulation samples, which is about **25–30% of the 391–455 s wall clock**, roughly 1.5–2 minutes.

Ownership: this is **`com.live2d.graphics3d.editableMesh` (host mesh code)** and unrelated to the 020 texture atlas image generation; fixing it means rewriting the host triangulation (and honouring the `l.equals` semantics), with a completely different risk and acceptance surface. This report only locates it and implements nothing; pushing it forward needs its own feature and a separate decision.

### Limits

- Still **one run per tier** with no repetition and no pairing, so it is still no SC-02 or SC-04a evidence.
- The scenario pins the layout scale to 40%; a real user who does no automatic layout sees a different magnitude of atlas generation.
- The absolute durations include the cost of the validation harness (isolated prefix, three agents, JFR overhead).
- JFR sampling is statistical and serves only hot-spot and phase-boundary location.
- This round is **measurement only**: no production code changed and no optimized-versus-unoptimized pairing was measured.

## Limits (Not to Be Crossed)

- **The fixture is tiny**: Circle100 is 100 images of 100×100. A real model with larger and more numerous images raises the texture generation share significantly, so the 8.8% of this round **cannot be extrapolated** into a user-site ratio.
- There is only **1 run** with no repetition and no pairing, so it is no performance evidence for SC-02 or SC-04a; a `runElapsedMillis` difference against another job is neither a gain nor a regression.
- JFR sampling is statistical (about 50–100 samples per second) and can locate only hot spots and phase boundaries, not exact per-method durations.
- This round **only measures**: no production code changed and no optimized-versus-unoptimized pairing was measured, so it carries **no speedup evidence**.
- The JFR was captured inside the validation harness (isolated prefix, agents, local queue), so the absolute values include harness overhead.
