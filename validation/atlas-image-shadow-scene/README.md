# T040 atlas-image-shadow Standalone Scenario

This directory implements only the offline preparation of T040: a minimal UI capture driver for the fixed 5303 / Circle100 case, the T039 fixed freeze API bridge, payload persistence, and a blocked bundle wrapper. It modifies no T036 probe, Runner, kernel probe, SDK, core, or settings.

## Fixed Boundary

- The input source comes only from the ignored `.env` or environment entry `TURBOISM_HOST_VALIDATION_FIXTURE_5303`. The source basename must be `atlas_mapping_100.cmo3` with SHA-256 `2866a509322496680500090cb26432b1b59fe30404e1f5e2163536c01a8dce4e`.
- The Runner copies the source to `{TASK_ID}-atlas_mapping_100.cmo3`; the driver strictly compares the expanded `fixtureName` with the basename of the real copied file and never treats the source suffix as the copied name.
- The UI matches exactly the unique fixture main window, the `Modeling -> Texture -> Edit Texture Atlas...` menu, the unique `OK`, and then the `Automatic layout...` button inside the editor plus the host layout dialog it opens. The host integer downsampling kernel is called only when the effective scale is at most 0.45, so the scenario selects a `user specified` scale in the layout dialog. The scale is the only per-job parameter of this scenario and the wrapper selects it strictly from the `{runLabel}` suffix (`-scale40` means below 0.45 and must hit the kernel; `-scale60` means above 0.45 and must take only the Graphics2D fast path; any other `-scale<number>` fails closed; no suffix defaults to 40). It passes as `turboism.validation.atlasImageShadow.layoutScalePercent`, the driver re-checks it against a two-value allowlist (dialog `com.live2d.cubism.doc.modeling.ui.atlasEditor.a.f`, scale control `com.live2d.ui.control.a.a.j`), and the dialog's own `OK` applies it. No other parameter changes, no CMO3 is saved, and nothing is exported.
- The close poll after OK continues only after a "quiet window set" and never clicks Save or any other button by default. A real 5303 host floating window is an ordinary `javax.swing.JDialog` (`com.live2d.ui.window.m`), while the driver's own menu popup is a heavy-weight popup. Right after the readiness gate the run samples one host window baseline by window identity; a window already in the baseline never takes part in the decision, only windows that appear after the baseline are considered, and only a **modal** window (`Dialog.isModal()`, the kind that can swallow input and can masquerade as a save prompt; the real 5303 `jp.noids.framework.e.a.f` progress window uses `setModal(true)`) blocks. A new non-modal window (popup, host palette) is recorded but never blocks. After dispatching the menu action, `clearSelectedPath()` clears the driver's own popup.
- T039 is called only through the fixed reflective entry `dev.turboism.validation.atlasimage.t039.T039ShadowAgent.freezeCapture(String)`; no T039 implementation or generic host reflection is copied. The bridge validates the flat `Map<String,String>` against the exact 43-key schema of the delivered source and REPORT and rejects a missing or unknown field; the offline self-check map is a strict same-schema stub, and the real artifact gets a separate pure-JDK bridge reflection regression.
- The freeze must bind the current runId and must report `state=SHADOW_READY`, `removalStatus=REMOVED`, `candidateReturnedCount=1`, `transformerRegistered=false`, `frozen=true`, and `fullBoundsPreserved=true`. `NO_CALLS`, `NO_ELIGIBLE_CALLS`, `POTENTIAL_TRIM`, and `TRUNCATED` are classifications and prove neither coverage nor a working optimization.
- The order is fixed: the unique OK completes and the editor closes → T039 freeze → payload write, close, re-read, and hash verification → one `collectionStatus=COMPLETE`; before publishing canonical, the loop handles a short write, then fully re-reads after force and verifies the four fixed fields, and a truncation, write failure, or zero progress publishes no COMPLETE → the single native quit menu. A failure attempts only one `collectionStatus=FAILED`, and a failed write leaves no canonical result. Before confirming the editor, the run performs one layout pass: click the unique `Automatic layout...` (the host `APPLICATION_MODAL` dialog blocks the EDT until its own OK closes it, so the driver posts the click first, waits for the window, and then configures and clicks its OK from a second EDT action), and `layout.dialogSeen`, `layout.dialogMillis`, `layout.scaleText`, `layout.applyElapsedMillis`, and `layout.closed` are the bounded evidence; a scale field the host rejects fails closed and stops the capture.
- Whether the native exit returns is not a capture success condition; normal exit and containment are accepted by the queue lifecycle. After COMPLETE is published the exit is best-effort: the click is posted fire-and-forget (the host exit action may terminate the JVM directly and never report completion), and the driver never rewrites a completed capture as a failure because the exit did not return. When the host closes a document with unsaved changes it asks with its own option panel (`com.live2d.util.UUOption` builds three buttons from the Look-and-Feel `OptionPane.yesButtonText`, `noButtonText`, and `cancelButtonText` and shows them modally through `JOptionPane`); the fixture must stay byte-identical, so the scene may answer only **do not save**, and only by clicking the single no-button inside the single option pane, with the expected label read from the same Look-and-Feel resource, never hardcoded and never logged as localized text; when it cannot decide, it clicks nothing and records the reason. Within a bounded window (20 s, `EXIT_PROBE_SECONDS`) it observes and records `nativeExit.clickMillis`, `exit.windowSamples`, `exit.windowCount`, up to 3 deduplicated structural class names in `exit.windowClasses`, `exit.promptSeen`, `exit.promptAnswer`, `exit.promptButtonCount`, `exit.promptClasses`, `exit.promptMillis`, `exit.nonDaemonThreadCount`, and `exit.nonDaemonThreadNames` (same character allowlist and truncation), so structural evidence can diagnose what blocked the exit. The driver calls no `System.exit`, kill, shutdown hook, external hook, client, or collector.

## T039 Runtime Source Binding and Runner 5303 Facts

The unified Runner, the 5303 official BAT, and the latest T039 runtime binding were read only. The Runner `--jvm-option` expands only `{TASK_ID}`, `{HOME}`, `{FIXTURE}`, and `{FIXTURE_NAME}`; there is no `{CUBISM_JAR}` or build-machine path placeholder. The 5303 Runner clones the official Proton prefix into the `prefix` of each task and then calls the fixed `C:\Program Files\Live2D Cubism 5.3.03\CubismEditor5.bat` inside that isolated prefix. The official BAT first runs `cd /d "%~dp0"` and then starts with the relative classpath `app\lib\Live2D_Cubism.jar`, so the only candidate inside the JVM is the Windows path `C:\Program Files\Live2D Cubism 5.3.03\app\lib\Live2D_Cubism.jar` inside that task prefix. The path string is fixed because each task uses its own prefix, not because of a build-machine golden path, and it is not the Z: mapping of `{HOME}` or `{FIXTURE}`.

The wrapper and build manifest pass only `sourceBinding=target-pd` and the single `trustedSourcePaths` candidate above; `--t039-code-source` and `TURBOISM_ATLAS_IMAGE_SHADOW_T039_CODE_SOURCE` are read only during an offline build or publish to verify the official JAR and its fixed SHA, and never become a runtime property. Inside the real JVM, T039 takes the `file:` CodeSource from the ProtectionDomain of the first target definition, runs `toRealPath()`, requires a unique candidate with the exact path, loader, and JAR SHA, and re-checks before it returns the candidate; anything else is refused. When a real launcher or classpath no longer satisfies these facts, this scenario stays blocked and never guesses a Unix or Windows mapping or switches to a host path.

The same facts are the driver startup gate: `DriverConfig.fromSystemProperties()` does not read `t039.codeSource` but requires `sourceBinding=target-pd` plus one absolute `trustedSourcePaths` candidate ending in `Live2D_Cubism.jar` (a pure string shape check so it stays offline reproducible); the real canonical, ProtectionDomain, loader, and hash verification still happens inside T039. The offline regression feeds the complete JVM property set planned by the Runner `--dry-run` into the real `fromSystemProperties()` and asserts that removing `t039.sourceBinding` or `t039.trustedSourcePaths` is refused.

## EDT and Evidence

`FixedEdt` serves only this fixed scenario and separates two budgets: the **queued startup budget** and the **query budget of a started action**, each a 5-second bounded wait. A queued callback becomes `TIMED_OUT` atomically on timeout or interrupt, and a late callback is recorded as skipped and never executes. A `STARTED` action cannot be undone and is never claimed rolled back; the fixed query budget only reports it and no longer treats "the host has not finished" as "the action did not happen". The menu `doClick` start barrier, the synchronous modal OK action, and the modal action completion latch are separate so a synchronous modal menu action fits.

The driver starts in premain, before the host finishes its own bootstrap, so it passes a readiness gate before driving the UI: three consecutive EDT round trips must each complete within 1000 ms; any slow or queued round trip resets the count and increments `readiness.slowRounds`, which prevents a start while the host still occupies the EDT. The real 5303 `OK` runs the texture atlas rebuild synchronously on the EDT and may take far longer than 5 seconds, so the driver treats pressing `OK` only as the start point, then polls for editor close within the overall run deadline (a pure read poll interrupted by a queued timeout is only recorded and continues), and then waits for the modal action to end; a timeout still retries within the overall deadline and never declares a failure early.

Every run atomically replaces one bounded `driver-stage.properties` with real newlines that records the stage, time and duration, the EDT queued, started, completed, timedOut, and lateSkipped counters, the readiness gate rounds and slow rounds, the OK dispatch and wait durations, the fixed boolean state, and the last operation; it records no window title, model content, or unbounded event history. The driver safely creates the fixed output parent in a clean task home and claims `state/atlas-image-shadow/<taskId>` atomically with `CREATE_NEW`; a duplicate, a lost concurrent claim, a symlink, or an out-of-bounds path fails closed. The startup window lookup uses at most a 240-second startup budget; that is no performance threshold and never retries a started action.

The close poll samples until `CLOSE_POLL_TIMEOUT_SECONDS` (240 s): it continues to freeze only when the editor has closed and no modal window remains, and it fails closed when the budget runs out instead of misjudging on the first window it sees. It writes `editor.closePollVisible`, `editor.closePollUnexpected`, `editor.unexpectedWindowCount` and `Classes` (modal, blocking set), `editor.nonModalWindowCount` and `Classes` (non-modal, tolerated set), `editor.closePollMillis`, `editor.closePollTimedOut`, and `baseline.windowCount` and `baseline.windowClasses` into bounded evidence (at most 3 allowlisted and length-truncated class names per category, with no title, model content, or unbounded history).

## Host Capture Results (5303 / Circle100)

The T039 integer downsampling kernel `com.live2d.util.f.g.a(II[III[IIIII)V` has exactly one call chain in the whole JAR: `CTextureAtlas.setupCacheImage$cubism` → `D.a(CWritableImage, ui.g, CWritableImage, I, I, Z)` (mask=32 takes the default double `0.45`) → `g.a(BufferedImage, Graphics, BufferedImage, I, I, D, Z)`; that seven-argument method compares `min(|sx|,|sy|)` with `0.45` at offset 166, and **only an effective scale at or below 0.45** enters the branch that calls the kernel, otherwise it takes the UtCache temporary image plus `Graphics2D.drawImage` fast path. Four host captures turned that condition into a checkable fact:

| Run | Layout scale | `freeze.sampleOutcome` | `stats.eventLimit` | `recorded`/`dropped` | `admitted`/`potentialTrim` | Last real parameters |
|---|---|---|---|---|---|---|
| job 8 `queue-de28907537e447128af8f25bd2af14cb` | no layout (current page 1:1) | `NO_CALLS` | 16 | 0 / 0 | 0 / 0 | — |
| job 9 `queue-bbe77b2627ba4c61bad9009516692145` | user specified 40% | `TRUNCATED` | 16 | 16 / 84 | 16 / 16 | kx=2 ky=2 padding=2 source=100×100 stride=104 destLen=10816 full=100×100 |
| job 10 `queue-6b482897236f4d939bc392fa84e51c76` | user specified 40% (window widened to 64) | `TRUNCATED` | 64 | 64 / 36 | 64 / 64 | same (2×2 downsample) |
| job 11 `queue-53c2672283984acf91e34dd1c5c90269` | user specified 60% (reverse control) | `NO_CALLS` | 64 | 0 / 0 | 0 / 0 | — |

All four are 5303 queue PASS (`state=succeeded`, `validationStatus=PASS`, `normalExit=true`, `identityVerified=true`, `fixtureUnchanged=true`), and the fixture stayed byte-identical throughout (the scenario never saves, and the exit prompt is answered with do-not-save). Driver evidence: job 9 `layout.dialogMillis=585`, `layout.scaleText=40`, `editor.closePollMillis=11902`, `runElapsedMillis=87388`; job 10 `layout.dialogMillis=408`, `layout.scaleText=40`, `editor.closePollMillis=9797`, `runElapsedMillis=109059`; job 11 `layout.dialogMillis=244`, `layout.scaleText=60`, `runElapsedMillis=93940`; all three layouts reported `layout.dialogSeen=true` and `layout.closed=true`.

Conclusion and limits: the kernel trigger is the host layout scale, not a driver defect. Both job 9 and job 10 produced 100 kernel calls (job 10 recorded 64 and dropped 36), and the first 64 recorded calls were all `admitted=true` with `potentialTrim=true` at 2×2 downsampling; job 11 at 60% produced **0 calls**, which together with the 1:1 job 8 confirms from the other side that only an effective scale at or below 0.45 reaches the kernel. `freeze.sampleOutcome=TRUNCATED` only means the bounded event window of T039 (`stats.eventLimit=64`, already the T039 maximum) filled up, and the `recorded`, `admitted`, and `potentialTrim` counters advance only while the window has room, so this is still a **prefix classification of 64 of 100 calls**, not the full hit rate over 100 calls; a full classification needs a change of the T039 counting semantics, which belongs to the T038 and T039 delivery and not to this scenario. `stats.methodExecuted=false` is the expected shadow-ready value (the original method body does not run and the candidate returns the full bounds unchanged).

The per-job scale selection is itself the control condition of this reverse comparison: job 10 and job 11 use byte-identical driver, T039, and production agent code and differ only in the `{runLabel}` suffix (`-scale60`) that reaches `turboism.validation.atlasImageShadow.layoutScalePercent`.

Parameter distribution and paired performance (SC-02 and SC-04a) are still open: the current evidence proves only that the real entry reaches that kernel, records the real parameters, and can be steered on both sides of the threshold by the scale. It cannot replace paired timings, CPU, and memory measurement with the optimization on and off, and the `runElapsedMillis` differences of job 9, 10, and 11 (87–109 s) are neither a gain nor a regression.

## Build and Offline Verification

```bash
TURBOISM_HOST_VALIDATION_FIXTURE_5303=/path/from/ignored/.env/atlas_mapping_100.cmo3 \
  bash validation/atlas-image-shadow-scene/build-and-selfcheck.sh
TURBOISM_ATLAS_IMAGE_SHADOW_T039_AGENT=/path/to/explicit/t039-shadow-agent.jar \
  TURBOISM_ATLAS_IMAGE_SHADOW_T039_CODE_SOURCE=/path/from/ignored/Live2D_Cubism.jar \

```

`TURBOISM_ATLAS_IMAGE_SHADOW_T039_CODE_SOURCE` is a read-only build-time reference; it is never written into `trustedSourcePaths` and never used to guess the runtime CodeSource of the task clone.

Optional runtime run-label suffixes (all fail closed, and the default behaviour is unchanged):
- `-scale40` or no suffix means 40% (below the host 0.45 threshold, so the kernel is hit); `-scale60` means 60% for the reverse control; any other `-scale<number>` is refused, and a repeated or malformed suffix is refused too.
- `-jfr` additionally injects `-XX:StartFlightRecording=filename={HOME}\atlas-profiling.jfr,settings=profile,maxsize=256m,dumponexit=true` for the T029 bottleneck measurement; it changes no scenario action, parameter, or result file.
- `-heavy` switches to the production-scale fixture `heavy.cmo3` (SHA-256 `029e9a4e…`, from `TURBOISM_ATLAS_IMAGE_SHADOW_FIXTURE_HEAVY_5303`) and raises the wall-clock budgets to 1800 s for startup and close polling, 900 s for the layout dialog, 3600 s for the driver, 3600 s for the result, and 300 s for the exit. That profile needs its own published manifest (`build-and-selfcheck.sh --publish --fixture-profile heavy`) because a manifest pins one fixture identity pair.

The only per-job runtime parameter is the layout scale: the wrapper selects it from the `{runLabel}` suffix (no suffix or `-scale40` = 40%, `-scale60` = 60%, any other `-scale<number>` fails closed) and passes it through `-Dturboism.validation.atlasImageShadow.layoutScalePercent`.

The build uses JDK 17 with `-Xlint:all -Werror`, and the ordinary compile classpath holds no official Cubism JAR, T039 source, or host class. The self-check covers:

- the exact 43-key T039 schema, a wrong run, a missing field, a non-flat scalar, an unknown field, and the four sample classifications; the shell regression performs a pure-JDK public-static bridge check with the explicit T039 agent JAR and defines or executes no official class;

- `hostExecuted=false`. The own fake editor enters only the self-check JAR and never the production driver JAR;
- the wrapper offline regression additionally asserts that the default run label produces `layoutScalePercent=40` and `-Dturboism.validation.t039.maxEvents=64`, that `-scale60` produces `layoutScalePercent=60`, that `-scale55` fails closed and produces no `layoutScalePercent`, that the startup property contract accepts the planned property set and rejects `layoutScalePercent=55`, and that it rejects a plan with `t039.sourceBinding` or `t039.trustedSourcePaths` removed.
